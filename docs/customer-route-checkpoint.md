# Customer product route checkpoint

`/customer/` is now explicitly built and linked from the customer access panel. It is a product shell, not a local brief/demo: there are no embedded customer identities, inventory fixtures, browser answer persistence or fallback workspace. `/customer-preview/` stays local-only; its two fixture scripts are also excluded from the public build.

The route loads only from the server customer API. The customer selector (`?customer=...`) is an untrusted routing hint, never authority. Server verification of the selected provider identity and a nonexpired, nonrevoked assignment is mandatory on every operation. Netlify owner sign-in alone grants no customer assignment. The existing deployed customer function still returns 503 for every method; opening the route currently displays an unavailable notice and accepts no answers.

The future orchestration adapter must return `{template,draft}` after assignment verification. Template contract: `id`, integer `version`, `kind: 'pesmera-inventory'`, `fixture: false`, `name`, six ordered `steps` with `title/why/example`, optional source `label/checkedAt`. Draft contract follows CustomerService: `schemaVersion: 1`, matching template id, integer revision, answers and completed photo IDs. The PostgreSQL repository currently returns database records, not this UI envelope; a verified template resolver/envelope adapter is still required. Initial source inventory must be resolved server-side, never imported from the demonstration. An absent customer selector must either resolve the authenticated assignment unambiguously or be denied by the configured server adapter.

The UI supports guided responsibility, inventory, package composition, language, additional questions and review/back/edit. Save uses POST `operation:save` and expected revision, and accepts only a matching versioned response. Submit requires a saved version and repeats that same revision after errors. Pending receipts never claim completed delivery. Authentication denial wipes rendered private answers. Photos remain explicitly unavailable; no photo picker accepts files. Server receipts alone do not prove catalog update completion: update status is shown separately. Validated automatic updates remain required, without adding an approval gate.

Validation: 72 Node tests passed; six-page static checks passed with Python UTF-8 enabled; production build contains 38 files. New browser test exercises the built route at 320/393/768/1280px with synthetic intercepted API responses: 401, 403, 503, owner-shaped response rejected, assigned guided flow, review/edit, plain-text HTML-like input, interrupted save, conflict, reload from server-shaped state, duplicate version retry, pending/downstream receipt and revocation wipe. All four widths pass. No live customer authentication, database, upload, cross-device cloud persistence or Notion writes are established by these tests.

Remaining configuration boundary: approved organization/project provisioning and credential setup are pending separately; configure customer Supabase authentication and server-only assignment resolver; migrate/restrict staging storage; verify template/source mappings; wire durable orchestration and worker credentials only after approval; provide decoder/scanner and private upload UI; verify destination mapping and automatic catalog update scope/snapshot protection. No runtime secrets or provider resources were created. Keep all real mutations disabled until those boundaries are approved and implemented.
